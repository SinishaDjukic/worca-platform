# Decisions

Decided on 2026-10-06 unless a row says otherwise. Each decision has a number so other documents
and later changes can refer to it. To change one, edit its row and note the date and reason;
don't delete it.

## Platform shape

| # | Decision | Why |
|---|---|---|
| D1 | *(worca.run deployment)* The control plane is a Cloudflare Workers app at `app.worca.dev`, in this repo (`worca-run`), separate from worca. | Tenant management, sign-up and provisioning are a different product from worca itself. Workers give us D1, Workflows and KV with no servers to run. |
| D2 | Stack: Hono, Better Auth, D1, Cloudflare Workflows, KV, Resend for email. The Cloudflare account is on Workers Paid, which covers Durable Objects and Workflows; the `worca.run` zone itself is on the Free plan (D55). | Better Auth is open source with no per-user fees and already has organizations, teams, invites, email codes, passkeys and per-org SSO. Workflows give durable, retryable provisioning steps. |
| D3 | Cloudflare Access is not used for SaaS instances. The control plane and the gate Worker replace it. | Access has no sign-up, organizations or per-instance roles, is priced per seat above 50 users, and doesn't cleanly support "any Microsoft account". |
| D4 | Every instance runs in its own Railway project: worca, the credential broker and cloudflared, plus a volume. Railway Pro plan. | One project per instance gives each tenant its own private network and keeps their credentials apart. Hobby's 5 GB volume cap is too small. |
| D5 | One Cloudflare Tunnel per instance, never shared. | Every connector of a tunnel serves all of its hostnames, so a shared tunnel would let one tenant's cloudflared receive another tenant's traffic. |
| D6 | *(worca.run deployment)* Everything runs in the EU by default: D1 with the EU jurisdiction, Railway's EU region, Resend's EU region. | The expected customers will ask for it. |

## Domains and naming

| # | Decision | Why |
|---|---|---|
| D7 | *(worca.run deployment)* Instances live on a separate domain, `worca.run`. The control plane stays on `worca.dev`. | Instances run agent code. On the same registrable domain they would be the same site as the control plane, so they could set cookies for it and bypass SameSite protections. |
| D8 | Instance hostnames are random, one level deep: `{slug}.worca.run`, slug = 10 characters of base32 without look-alike characters. | Org names don't appear in public hostnames. One level stays inside the free wildcard certificate. A wildcard certificate also keeps individual hostnames out of certificate transparency logs. |
| D9 | The broker's key page gets its own random slug, separate from the instance's. | The broker design requires the key page on its own hostname, isolated from worca's pages. |
| D10 | *(worca.run deployment)* Slugs are assigned once and never change. Reserved: `www`, `api`, `status`, `mail`. The apex `worca.run` redirects to `worca.dev`. | Stable links; room for platform hostnames later. |
| D11 | *(worca.run deployment)* `worca.run` sends no email: no MX record, SPF `v=spf1 -all`, DMARC `p=reject`. Email goes out from `worca.dev`. | Nobody can send mail that appears to come from an instance domain. |
| D12 | *(worca.run deployment)* Apply for `worca.run` on the Public Suffix List. Until it is listed, the gate Worker enforces isolation between instances (see [Security](security.md)). | Once listed, browsers treat every instance as its own site. Listing takes weeks to months to reach users' browsers. |

## Roles and access

| # | Decision | Why |
|---|---|---|
| D13 | Roles are scoped bindings on one user account, not separate user types. | One person can be platform staff and a tenant member; each role is granted and revoked on its own. |
| D14 | Platform roles: **superadmin** (system settings, all platform role bindings), **admin** (tenant processes, tenant invites, tenant limits, but not platform roles), **support** (read-only status). | Least privilege for platform staff. |
| D15 | No platform role can enter a tenant instance. Platform staff see only status: running or down, worca version, pipeline counts, whether it can be suspended. | Tenants' code and data stay private from the platform operator. |
| D16 | Platform superadmins and admins may stop an instance for abuse. It is logged and the tenant admins are notified. *Changed 2026-10-06: was "stop or suspend"; suspending is now for idle instances only (D47).* | Abuse response must not depend on the tenant. Stopping is not reading. |
| D17 | Tenant = organization. One org per tenant. | Simpler model. |
| D18 | Tenant roles: **tenant admin** and **tenant user**. Every tenant admin is an owner with full rights, including deleting the org. There is always at least one tenant admin. | No separate owner role needed. |
| D19 | Access to instances only through teams: user → teams → instances. No direct user-to-instance grants. A user can be in several teams. | One way to grant access keeps it understandable and auditable. |
| D20 | The team-to-instance link carries an optional role field, empty in v1. | Room for "viewer vs operator" later without a migration. |
| D21 | One person can belong to several orgs, with an org switcher in the control plane. | Consultants and contractors. |
| D22 | Sign-in happens once, on the control plane. Methods: email code, Google, Microsoft (any tenant), passkey, and the org's own SSO (OIDC or SAML) tied to a domain the org has proven it owns. | One Google project and one multi-tenant Microsoft app serve the whole platform. Passkeys give phishing-resistant sign-in without passwords. |
| D23 | Login policy is set per org (allowed methods, optional required email domain). Each instance can only narrow it, e.g. "this instance requires SSO". | Per-instance methods can't work when sign-in happens once, but instances can demand more. |
| D24 | MFA (or a passkey) is required for platform roles, and for tenant admins before any destructive action. | Protects the accounts that can do the most damage. |
| D25 | Registration launches as invite-code only, then waitlist, then open. One setting switches the mode. | Control growth and cost before opening up. |

## Instance lifecycle

| # | Decision | Why |
|---|---|---|
| D26 | Tenant admins are notified of new worca versions and decide when to upgrade. They may postpone indefinitely. *Confirmed 2026-10-06 (Q8): this holds for security fixes too; the platform never upgrades an instance on its own. A tenant admin starts every upgrade and a Workflow carries it out.* *Addendum 2026-10-07: the tenant admin picks the version, any published one from MIN_HOSTED_WORCA_VERSION up, also one older than the instance runs (a downgrade, to step back from a bad release; the console warns that a newer version's data may not be readable). Downgrades are started the same way and audited with their direction.* *Amended 2026-10-07: the one exception to "only tenant admins upgrade" is automatic micro updates. Per instance, `auto_update` is `micro` (new instances) or `off` (instances that existed before, until their admins turn it on; tenant admins switch it either way). With `micro`, the platform installs a newer micro release of the running major.minor (1.9.1 → 1.9.2, never 1.9 → 1.10 or a prerelease) while the instance is idle, through the same upgrade Workflow and rollback, audited as the system and mailed to the tenant admins. A version that rolled back, or that a tenant admin downgraded away from, is skipped until a newer micro is published. Minor and major versions stay the tenant admin's decision.* | Tenants control when their instance changes; micro releases (fixes) reach idle instances without anyone having to act, unless the tenant turns that off. |
| D27 | Idle instances are suspended, but never while pipelines are running or scheduled. The heartbeat reports whether the instance can be suspended. The gate wakes a suspended instance on the next visit. *Changed 2026-10-06: idle means 24 hours with no session check in the instance's gate object (D43), timed by that object's alarm instead of a Cron Trigger.* | Saves compute without breaking work. |
| D28 | Instances send a heartbeat to the control plane: health, worca version, pipeline counts by status, and whether they can be suspended. No pipeline titles, prompts, branches or IDs. *Changed 2026-10-06: also the time of the next scheduled run, if any (D56).* | Enough for status and suspension; nothing that is tenant data. |
| D29 | Deletion is immediate and permanent. No soft delete, no grace period. | Explicit requirement. |
| D30 | Destructive actions need two confirmations: in the UI (type the name), then an emailed link. The link opens a page with a confirm button; it never acts on a plain GET. Single-use, 30-minute expiry, only for the user who started it, who must be signed in. Other tenant admins are notified afterwards. | Mail scanners prefetch links, so a link that acts on GET would fire by itself. |
| D31 | Destructive actions include: deleting an instance or the org, removing the last tenant admin, resetting an instance, and changing the login policy in a way that locks members out. | |
| D32 | No platform backups of instance volumes in v1. | Hard delete must leave nothing behind. Code lives in git; worca's state is disposable. If backups are added later, they are encrypted with the org's key. |
| D33 | *(worca.run deployment)* Free-tier limits: 1 instance per org, 2 vCPU / 4 GB per instance, 10 GB volume, 10 members. Enforced by the control plane, with per-service resource limits set at creation. *Refined by D78: Team and Business tiers, compute sizes per instance.* | Railway's own spending cap covers the whole workspace, so per-tenant limits are ours to enforce. |
| D34 | Agents' outbound network traffic is limited to an allowlist per instance, using worca's existing egress filter, plus CPU alerts. *Refined by D73: an org policy with per-instance overrides, open by default.* | Agents run arbitrary code from our Railway account; mining, spam or attacks would come from our IPs. |
| D35 | GitHub: one platform-wide GitHub App that each org installs on its own GitHub org. Personal pushes use the broker's "push as me". | One app to maintain; each org controls what it grants. |

## Data protection

| # | Decision | Why |
|---|---|---|
| D36 | All tenant data in the control plane database (not metadata) is encrypted with application-level keys: one data key per org, one per user, each encrypted under a master key. | A leaked database export or backup reveals nothing. Destroying a key destroys that org's or user's data, including any copies. |
| D37 | The master key is a Workers secret, with an offline backup split between two superadmins. Rotating it is a superadmin action. | Losing the master key loses every tenant's data. |
| D38 | Tenant admins can rotate their org's data key. | Tenants can respond to their own incidents. |
| D39 | Team names are tenant data and are encrypted. | |
| D40 | Every operation by anyone, platform or tenant, is recorded in an audit trail. Kept for 30 days (D57). | Accountability on both sides; required for abuse handling (D16). |
| D41 | Tenant admins can see their own org's audit log. | Transparency, including about platform actions on their instances. |
| D42 | *(worca.run deployment)* Legal documents (terms of service, privacy policy, data processing agreement) are needed before opening registration, prepared with a lawyer. | We process customers' code and personal data. |
| D49 | Session tokens and one-time codes are stored only as hashes. A session's IP address and user agent are encrypted with the user's key. | Better Auth stores the session token in plaintext by default, so a leaked database export would hold live sessions. |

## The gate's state and sessions

Decided on 2026-10-06, after checking Cloudflare KV's consistency and Railway's API.

| # | Decision | Why |
|---|---|---|
| D43 | Each instance has one Durable Object (the *gate object*), created in the EU jurisdiction. It holds the instance's status, its live gate sessions, its last visit and whether a wake is under way. KV keeps only hostname → instance id. | KV is eventually consistent: changes and deletions take 60 seconds or more to reach other locations, and missing keys are cached too. A Durable Object is strongly consistent. Slugs never change (D10), so caching hostname → id in KV is safe. |
| D44 | The gate cookie carries a pass valid for 60 seconds, encrypted and signed by the gate. GET and HEAD requests with a valid pass go through without asking the gate object. The gate object is asked when the pass runs out, and on every request that changes state and every WebSocket upgrade. Reads that return secrets (worca's raw model env) are asked every time too. | Asking the gate object on every request would add a round trip to the EU to every page load, script and API call. This way an active user costs about one call a minute, and requests that change state are still checked every time. |
| D45 | The gate renews the identity token itself, server to server over a service binding to the control plane. The browser is redirected to `app.worca.dev` only when the control-plane session has ended; requests that aren't page navigations then get a 401, and worca reloads the page (W6). | A redirect can't renew a token for an API call or a WebSocket. |
| D46 | Removing someone from a team or org, unassigning a team from an instance, disabling a user and signing out all drop the affected gate sessions in the gate objects concerned. worca closes a WebSocket when the token it was opened with expires (W7). | Requests that change state are refused at once, reads within 60 seconds, open WebSockets within the token's lifetime. |
| D47 | Two separate statuses: **suspended** is for idle instances only and wakes on the next visit; **stopped** is for abuse only, doesn't wake, and only platform staff can lift it. | "Stop or suspend for abuse" mixed the two, and a visit must never wake an instance stopped for abuse. |
| D48 | Suspending stops every service's latest deployment through Railway's API (`deploymentStop`); waking redeploys it (`deploymentRedeploy`). | Railway doesn't allow 0 replicas ("must be greater than or equal to 1"), and its app sleeping and serverless mode need minutes without outbound traffic, which cloudflared and the heartbeat never give. |

## Settled from the open questions

Decided on 2026-10-06, after research on Better Auth, Cloudflare, Microsoft and Google, or by the
product owner where marked.

| # | Decision | Why |
|---|---|---|
| D50 | Accounts are linked by email only when the provider vouches for it: Google's `email_verified`, Microsoft's optional `xms_edov` claim. Microsoft users are identified by `tid` + `oid`, never by `email`. | Microsoft's `email` claim is mutable and unverified ("never use it for authorization"); linking on it lets someone take over an account with another person's address (nOAuth). |
| D51 | Workers VPC is not used. The gate reaches each instance through its own proxied DNS records (Q2). | It is in beta, WebSockets through it are undocumented, and the binding that reaches many tunnels without a redeploy exposes the whole account network to the gate. |

About $21 a year. |
| D53 | The gate's KV namespace is created in the EU jurisdiction. | Matches D6. It holds only hostname → instance id; KV may still cache it outside the EU. |

The built-in token encryption uses one platform key, so destroying a user's key wouldn't erase them. |

| D56 | Schedules no longer prevent suspension. The heartbeat reports the next scheduled run; the gate object's alarm wakes the instance 10 minutes before it (Q9). | Instances with schedules would otherwise never be suspended. |

| D58 | *(worca.run deployment)* Abuse reports go to `abuse@worca.dev` or a form on `worca.dev`; both are linked from the "stopped" page and from `security.txt` on both domains (Q12). | Reporters use either; the form collects the instance hostname reliably. |
| D59 | Users can export their own data (profile, memberships, their entries in audit logs still kept) and delete their own account at any time, unless they are the last tenant admin of an org; they must first hand that over or delete the org (Q13). | GDPR access and erasure, without leaving an org with no admin (D18). |
| D60 | A tenant admin may delete an instance while it is stopped for abuse. *Product owner, 2026-10-06 (Q16).* | Hard delete (D29) applies regardless; the platform keeps only the 30-day audit record. |

## The web UI

Decided on 2026-10-06 after the [UI feasibility](ui-feasibility.md) review.

| # | Decision | Why |
|---|---|---|
| D61 | Platform staff see org names, instance names and the org admins' email addresses in the console. Instance contents stay hidden (D15). *Product owner.* | Support can't help "Acme" by org id alone. D15 is about tenants' work, not their names. |
| D62 | Every org member sees the member directory (name, email, role, teams), as in GitHub, Slack and Linear orgs. Only tenant admins see when people joined, how they sign in, pending invitations, and management actions. *Product owner: "a common industry approach".* | People need to know who else is in their org; the sensitive parts stay with admins. |

| D64 | Instances run worca's public image `ghcr.io/sinishadjukic/worca`. The broker is the same image with the start command `worca-entrypoint worca broker`. *Product owner: the image holds nothing sensitive.* | No registry credentials to manage. One image per version. |
| D65 | Gaps in worca found after W1–W7 go to the worca backlog (kept with worca-cc), not into this design: graceful drain, auto-resume on start, per-person Away mode. | worca is a separate project; the platform keeps a ready-to-pick-up list. |
| D66 | The web UI is plain ES modules and one stylesheet, with no framework and no build step, served by the control Worker from `ui/` (Workers static assets behind the Worker). Markup is built with an escaping tagged template. *Product owner, 2026-10-06.* | The same approach as worca's own UI, so both share their look and habits. Nothing to compile or update; every response still passes the session check and the security headers. Replaces the React/Vite plan in the UI concept. |
| D67 | *(worca.run deployment)* `worca.run` and `www.worca.run` redirect (301) to `worca.dev/hosted/`, answered by the gate Worker on its own custom domains. *Product owner, 2026-10-06.* | Instances live on subdomains, so the apex has nothing else to show. The deploy token can't create redirect rules; the gate already owns the zone's traffic. |
| D68 | Each instance's credential broker runs in multi mode. The create Workflow generates its shared secret (worca and broker) and its vault key, and they live only in the instance's Railway variables: no copy in D1, encrypted or not. | The vault key only decrypts the key store on the broker's own volume in the same Railway project, so key and data share one fate and a copy alone recovers nothing. Deleting the project (D29) erases both, with nothing left to crypto-erase. A copy in the control plane would let whoever controls it decrypt every person's provider keys. If the variable were ever lost, people re-enter their keys on the key page. worca's advice to keep a copy in a password manager is for self-hosters who rebuild services by hand. |
| D69 | *(worca.run deployment)* People ask for hosted worca with a form on worca.dev (`POST /api/public/access-requests`). The form always answers the same; the request counts only once the person confirms their address from an emailed link (a page on app.worca.dev that posts the token; nothing happens on GET). Only superadmins see and decide requests; they hear of new ones at once, then at most hourly. Granting mails a single-use registration code that works only for the requester's address. Each request's address, use case, company and staff message are encrypted with the request's own data key. An unconfirmed request is deleted, with its key, 7 days after its link expired; 180 days after a decision or sign-up the key is deleted and the personal columns emptied, keeping an anonymous row for the funnel counts. No address or request text goes into the audit log or the logs. *Product owner, 2026-10-07.* | A way in while registration is invite-only (D25), without staff typing codes into mails. Same answer for every address, so the form can't tell who has an account. Confirming first keeps typos and other people's addresses out of the queue. A code tied to the address can't be passed on. A key per request makes deletion final, database backups included (crypto-shredding), without touching other requests. |

## Newsletter

Decided on 2026-10-07 by the product owner.

| # | Decision | Why |
|---|---|---|
| D70 | *(worca.run deployment)* The control plane runs worca's newsletter. Anyone can subscribe on worca.dev with double opt-in; signed-in people subscribe directly from their account page (the address is verified). A subscriber chooses a release threshold (`major`, `minor` = major and minor, `micro` = every stable release, `rc` = everything with release candidates, or `none`) and product news on or off. Release mail is sent automatically when worca-cc's release workflow calls a signed hook; the level comes from comparing the version with the highest stable version announced before it. Every mail carries a never-expiring signed manage link and RFC 8058 one-click unsubscribe; "unsubscribe from everything" revokes every earlier link. Bounces and complaints suppress the address. Sending keeps 30 mails a day of the Resend plan for transactional mail and waits for the next day when that is used up. Addresses are encrypted with a data key of their own. Unconfirmed subscribers are deleted after 30 days; 30 days after an unsubscribe or a suppression the address is shredded (key deleted, address emptied), keeping only the blind index and status as a suppression list; deleting an account removes its address's subscriber. No log, audit entry or KV key holds an address. *Retention added 2026-10-07 at the product owner's request for state-of-the-art protection of personal data.* | Release mail is the main reason people come back after trying worca, and a hand-run list would be forgotten. Double opt-in, one-click unsubscribe and a postal address are what mailbox providers and the law expect from bulk mail. The reserve keeps sign-in codes working on the day a release goes out. |

## Teams and remote access

Decided on 2026-10-08 by the product owner.

| # | Decision | Why |
|---|---|---|
| D71 | Instances are created within a team and always keep at least one team. The create needs a team of the org and assigns it with the instance row; removing an instance's last team, or deleting a team that is some instance's only team, is refused until another team is assigned or the instance is deleted. The console leads a new org through its first team, then its first instance in that team. An instance can still be shared with more teams (D19). *Product owner, 2026-10-08.* | The hierarchy is teams first, then instances in a team. An instance with no team can be opened by nobody but is still paid for, and an org that skips teams never learns how access works. |
| D72 | Worca's terminal and actions are off on hosted instances by default. Only the org's tenant admins can turn either on, per instance, with an MFA session; platform staff cannot. Each change is audited in the org audit log; applying it restarts Worca. *Product owner, 2026-10-08.* | Both run as the Worca server user, not the isolated agent user, so they give everyone on the instance a shell with Worca's own permissions (its settings and environment, the broker secret included). That is the org's call about its own people, not ours (D15). |
| D73 | Outbound network policy (reworks D34): each org has one, `open` by default (nothing restricted), `block` (everything except a blocklist) or `allow` (only an allowlist; a blocklist carves exceptions, block always wins). An instance follows it, or has its own policy that replaces it as a whole until removed. Entries are hostnames (`example.com`, `*.example.com` for subdomains). The platform's own hosts (control plane, the instance's broker) are always allowed and can't be blocked. Only tenant admins change it; loosening needs an MFA session, tightening doesn't. Applying it restarts Worca; it is sent to Worca as `WORCA_EGRESS_MODE` / `_ALLOW` / `_DENY` and enforced once Worca supports it. *Product owner, 2026-10-08.* | A fixed allowlist breaks most real work (every package registry, git host and API an org uses) while open-by-default with an opt-in policy lets each org decide its own risk; blocklists cover the common "everything but these" case. Loosening widens what agents running arbitrary code can reach, so it is protected like turning remote access on (D72); tightening only reduces risk. |
| D74 | Platform staff (admin, superadmin: `instances.rotate`) can renew an instance's credentials, one instance or every instance at once: a new tunnel secret, broker secret and heartbeat credential. A running instance restarts its three services; a suspended or stopped one gets the new values for its next start. The broker's vault key is never rotated this way. The org's tenant admins are emailed when their instance restarts. *Product owner, 2026-10-23, after Railway's security incident of 2026-10-21.* | A breach at a provider that holds the instance's variables (Railway) exposes them all at once; renewing them by hand for each instance took a one-off script and an evening. The vault key only decrypts the broker's volume, which a variables leak doesn't expose, and renewing it would make every key people stored unreadable. Staff only: the secrets are the platform's, not the org's, and a tenant can't tell when a provider was breached. |
| D75 | Automatic updates (D26 as amended) also cover minor releases, per instance and off by default: a tenant admin can let an instance take the latest minor release of its major (1.9.4 → 1.10.1) under the same idle rules as micro releases. Minor needs micro on; a major is never installed automatically. A rolled-back minor update's mail asks the admin to check the instance. No org-wide default. *Product owner, 2026-10-23.* | Some orgs want to stay current without watching releases, but a minor release can change how Worca stores its data, so a failed one that rolls back is riskier than a micro: it is each org's choice per instance, never the default. |
| D77 | Stable releases of `@worca/app` are enrolled on the platform by themselves: the 5-minute cron reads npm, and a version newer than the enrollment floor (the latest when the check first ran) becomes deployable once its image is on GHCR and the image's version label equals the version. It becomes the latest when it is the newest, which offers it to every older instance (D26 step 1); a backport of an older line becomes deployable only. Release candidates are never enrolled. A version whose image reports another version is held for staff. Superadmins can switch enrollment off, publish by hand as before, and withdraw a release with a reason: nothing is created, upgraded or downgraded to it, automatic updates skip it, enrollment never brings it back, and when it was the latest the newest release left takes its place. Instances already on it keep running; their org admins get an email and a banner with the reason and choose when to move. Withdrawing can be undone. Automatic updates (D26 as amended, D75) take a release only after a soak time a superadmin sets (0 to 720 hours; none by default for now, product owner 2026-11-01); upgrades started by hand get it at once. *Product owner, 2026-11-01.* | Releases sat unpublished because publishing was a manual step nobody remembered (1.15.0 and 1.16.0, while Worca itself already showed 1.16 as available). A bad release has to be stoppable at platform level before it spreads, and the soak gives time for that before automatic updates reach instances; forcing instances off a withdrawn release would break D26. The label check exists because 1.14.0 was the 1.14.0-rc.4 image retagged: its heartbeat never reports 1.14.0, so every upgrade to it rolled back. |
| D76 | The images every deploy uses are recorded per instance (`deployed_images`), and a service whose image is older than what the instance's worca version deploys today is refreshed without a new worca version. Today that is cloudflared, pinned separately from worca. A refresh redeploys only cloudflared, with worca and the broker left running, and counts as done once Cloudflare sees only the new connector version. Tenant admins start it by choosing the current version in the version dialog ("Update components"). The 5-minute cron also refreshes every running instance on its own, whatever its automatic-updates setting and without waiting for idle. A suspended or stopped instance starts from the new image when it wakes. Audited, no mail. *Product owner, 2026-10-27.* | cloudflared 2026.10.2 fixed trust in compromised eMudhra intermediates (Cloudflare notice, 2026-10-26), but the pin only reached new instances and upgrades, and waking redeployed the old image. The connector belongs to the platform, often carries security fixes, and restarting it interrupts no run, so it shouldn't wait for a tenant's upgrade. |
| D78 | *(worca.run deployment)* Two more tiers next to Free (1 instance, 10 members): Team (5 instances, 25 members) and Business (10 instances, 50 members). An instance has a compute size: Standard (2 vCPU / 4 GB, 4 agents and 2 scripts at once, as before), Large (4 vCPU / 8 GB, 6 and 3) or XL (8 vCPU / 16 GB, 8 and 4). A size sets the Worca service's ceiling on Railway and `WORCA_MAX_PARALLEL` / `WORCA_MAX_PARALLEL_SCRIPTS`; the broker and the tunnel keep 2 vCPU / 4 GB. A tier lists the sizes its orgs may pick (Free: Standard; Team: Standard and Large; Business: all three) and the default for new instances. | D80 | Release candidates on the platform. Worca's `-rc.N` releases (npm's `rc` tag, image `worca:x.y.z-rc.N`) are enrolled from npm like releases, with the same image check, but never become the latest and are offered to nobody. | D79 | Git credentials per instance, set by the org's tenant admins on the instance page. For each host one credential the whole instance uses: GitHub, the org's **own** GitHub App (App ID, private key, optional installation ID; recommended) or one token; Azure DevOps, one PAT; Bitbucket, an access token, or an Atlassian API token with its email. Also per instance: the commit identity agents commit with, an optional clone allowlist, and who pushes go out as: the instance's credential, the person who acted when they connected GitHub (the default), or only that person (`WORCA_GH_AS_PERSON` off / `prefer` / `required`). Members connect their own GitHub on the instance's key page by pasting a token, which needs no setup by an admin from the Worca release that has B7; an admin can also enter the client ID and secret of the org's App so members can sign in with GitHub instead. Worca then clones, fetches, pushes and opens pull requests as the person who acted, with their own account (reads from the release that has B9); someone who hasn't connected GitHub gets the instance's credential. Every instance does this by default (`WORCA_GH_AS_PERSON=prefer`, also before an admin saves anything), so a member can work with their own GitHub on an instance with no credential at all. Credentials are written once and never shown again: the console shows what they are (App ID and name, token owner, last four characters). The control plane keeps them encrypted with the org key, writes them to the worca service (and the broker for the client ID and secret) and removes the ones no longer set. A running instance restarts Worca to apply them (and the key page when the client ID or secret changed), a suspended or stopped one on its next start, like remote access (D72). Adding or replacing a credential or the client secret, or changing the clone allowlist, needs a passkey session; removing one doesn't. A GitHub App or token is checked against GitHub when saved. No read/write token pairs and no platform-wide GitHub App for now. *Product owner, 2026-11-01.* | Hosted instances had no way to get a git credential: pushes and pull requests failed, and only public repositories could be cloned. The org's own App keeps its private key within that org; a platform-wide App would put one key that reaches every org's repositories in every instance's variables, which needs Worca to take tokens minted elsewhere first (D35 stays open for that). Kept in the control plane, unlike the broker's secrets (D68), because the operations that apply settings (reconfigure, wake, upgrade) work from the stored values, and the org key makes them erasable with the org. A pasted personal token needs no OAuth app; that it did was a coupling in Worca (B7). |
